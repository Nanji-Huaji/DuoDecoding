## 阶段一：CUDA Graph 修复 → 配对实验 → 否定结论

### 修了两个真 bug ✓

| Bug | 现象 | 修法 |
|---|---|---|
| **① 接线漏点** | `adaptive_tridecoding` 用共享字典 `cache_kwargs` 构造三个缓存，按字面形式写正则全部漏掉 | 改用 `graph_cache_kwargs = {**cache_kwargs, "use_cuda_graph": ...}` 副本，只挂 little/draft（target 是 γ=1 整段前向，开图无益）|
| **② 长度追踪不同步** | `prob_history` 越界（`n1=354` 而 `len=341`，差恰好 γ2+1）| 两处叠加：(a) 图模式下 `_prepare_generation_inputs` 仍以 StaticCache 内部计数为 `cache_start`，改为以 `_current_seq_len` 为权威；(b) eager 回退（`new_len>1`）不推进 `nnz`，导致下一轮把已在缓存里的 token 重新喂一遍 —— 回退后显式对齐 `runner.nnz = end_pos` |

修完后 N=2 冒烟通过（gen_ids 逐样本一致），说明修复本身正确。

### 配对 A/B（干净窗口 ✓ GPU0 空载 ✓ 交替顺序 ✓ N=40）

| 指标 | eager | CUDA Graph | 判定 |
|---|---|---|---|
| 准确率 | 0.25 (10/40) | 0.25 (10/40) | ✓ 一致 |
| 吞吐 | **11.40 tok/s** | 9.54 tok/s | ✗ **慢 16%** |
| 68M 草稿计算 | 10.29 s | 18.50 s | ✗ 1.8× 慢 |
| 1.1B 草稿计算 | 99.78 s | 183.38 s | ✗ 1.8× 慢 |

**决定：不采用** ✗。主方法接线撤回，`--use_cuda_graph` 默认关，历史结果不受影响。

> 根因当时未明，阶段四才找到（见下）。**不是**捕获成本（只占 29 s），**不是**
> StaticCache 全量注意力（被实验否定），而是 eager 回退路径踩在 StaticCache 上。

**规律**：`吞吐 ≈ 接受长度 / 每轮固定开销`，每轮开销在本族内 250~370 ms

```
RL 控制器版 14.37  ≈  纯规则版 14.26  ≈  固定 γ=16 14.37
```
⇒ **调度策略层已饱和**，动作空间只有一个标量时 RL 学不出东西。
这直接解释了"不用 RL 讲不通"的叙事困境。

## 阶段三：量化实验（两条路都走不通 ✗）

### 起点：用户指出"草稿模型相比目标模型并不是很快"

```
13B（4bit）单 token = 44.8 ms（从 q_target_only 反推）
1.1B（bf16）单 token = 18.5 ms
⇒ 草稿只快 2.4×，投机解码一般需要 5~10×
⇒ 本方法 69.6 ms/token vs 仅目标模型 44.8 ms/token = 慢 1.55×
```

### 实验一：把草稿也量化（`--draft_quantization 4bit`，flag 本来就存在）

| 配置 | 准确率 | tok/s | 1.1B 单次前向 | 接受长度 |
|---|---|---|---|---|
| `dq_base`（草稿 bf16）| **0.25** | **11.46** | **18.22 ms** | 4.20 |
| `dq_draft4` | 0.23 ✗ | 10.03 ✗ | 29.22 ms ✗ | 4.13 |
| `dq_both4` | 0.23 ✗ | 9.93 ✗ | 29.52 ms ✗ | 4.12 |

**结论：量化草稿严格更差** ✗。bnb 4bit 的反量化开销是逐层的，1.1B 这种小模型
开销大于收益；且 4bit 草稿更差 ⇒ 接受率下降 ⇒ 轮数变多。
（顺带：`should_quantize` 规则 `size > 20` 说明 1.1B/68M 永远不会被 auto 量化。）

### 实验二：验证"精度不对称"理论（用户回忆"之前没给目标加量化"）

历史日志确认 `qp_tri_g16_thr04.log` 里有 `will use 4-bit quantization` ——
13B 一直被量化，通过 `--target_quantization` 默认值 `auto` + `size > 20` 自动触发。

直接对照（target_only，N=12）：
```
target 4bit :  21.77 tok/s   45.9 ms/token
target none :  21.14 tok/s   47.3 ms/token   ← bf16 只慢 3%
```
**⇒ 精度不对称理论被推翻 ✗✗（我此前的推断是错的，撤回）**

真实原因：13B 单 token 前向根本不是权重带宽瓶颈：
```
bf16 权重 26 GB / 768 GB/s ≈ 34 ms（下界）   4bit 权重 6.5 GB ≈ 8.5 ms
实测 47.3 vs 45.9 ms —— 两者几乎相同，都远高于 4bit 的下界
⇒ 这 46 ms 是逐算子调度/固定开销主导，量化只省显存不省时间
```

**推论（重要 ✓）**：13B 单 token 46 ms vs 验证 16 token 101 ms
⇒ 边际成本 (101-46)/15 ≈ **3.7 ms/token** ⇒ 多验证 token 几乎免费
⇒ **接受长度是唯一杠杆**（与阶段二的规律一致）。

## 阶段四：启动开销能优化吗 —— 能，但集成方式把它做成了负收益

### 13B 微基准（`scripts/bench_target_graph.py`，4bit，γ=16 循环）

```
eager 57.48 → graph 35.54 ms/token   = 1.62× ✓✓
```
⇒ 启动开销**确实可优化**，约 22 ms/token 是逐算子调度开销。
（注：该脚本的阶段 A/C 用 γ=1 调用不触发前向，数据无效，只有阶段 B 可信。）

### 捕获成本（`exp_logs/capture_cost.txt`）

```
eager 建缓存+prefill+首步:  374.5 ms
graph 建缓存+prefill+首步:  908.7 ms  ⇒ 捕获开销 ≈ 534 ms/样本
```
每样本约 25 轮 × 22 ms ≈ 550 ms 收益 vs 534 ms 捕获 ⇒ **13B 上开图打平 ✗**。

### 但真实管线里图模式反而慢 1.84×（关键矛盾）

```
微基准（真实序列长度）:  eager 24.7 → graph 19.9 ms  ✓ 图更快
真实管线（ab_eager vs ab_cuda）: 18.50 → 34.01 ms    ✗ 图慢 1.84×
68M 同样: 5.42 → 10.07 ms                              ✗ 慢 1.86×
```

**被推翻的假设**（诚实记录 ✗）："StaticCache 让注意力按 max_length 全量算" ——
测了 384~896 五档，图在所有档位都更快、且与 max_length 无关 ⇒ **撤回**。

**真正的根因 ✓**：
```
真实管线里 1.1B 每轮只有 5392/1249 = 4.3 次前向（不是 γ2=16 次单步）
⇒ 每轮主体是「多 token 整段前向」⇒ new_len > 1 ⇒ 无法进图 ⇒ 走 eager 回退
⇒ 回退时缓存仍是 StaticCache ⇒ 拿不到图收益，还付了 StaticCache 的代价
⇒ 1.84× 变慢，端到端慢 16%
```

**修复方向（已实施，见 `docs/verify_graph_fix.md`）**：
1. 回退路径绕开 StaticCache（多 token 时临时用 DynamicCache 再搬回）—— 已被
   **padding 验证图**方案取代 ✓
2. ~~把多 token 前向拆成单步~~ —— **对验证前向是负优化 ✗**（每步整读一遍权重：
   13B bf16 21×34ms=714ms，比整段 eager 的 101ms 恶化 7×）。正确做法是
   **(1,K) 定长 padding 验证图** + 图跨样本复用 + 去逐前向 `.item()` 同步，
   2026-09-16 已实施，等价性测试通过，配对 A/B 见 `exp/vg_*`。

**收益上限（即使修好）**：每轮 365 → 约 293 ms ⇒ 14.37 → 17.9 tok/s（**+25%**）
—— 通信+排队 97 ms/轮（27%）完全不受影响，绝对瓶颈仍是接受长度 5.25。
（注：padding 验证图把 13B 验证前向也纳入图加速，实际收益可能高于此保守估计。）

> **2026-09-24 终局**（`docs/verify_graph_fix.md`）：padding 验证图已完成配对
> A/B（N=40×2，干净窗口）：准确率 0.25=0.25 ✓，吞吐 11.47→13.40 tok/s
> = **1.17×** ✓。归因修正：收益全部来自 1.1B（2.13×）与 68M（1.65×）；
> **13B 图回放几乎无收益（1.03×）—— 其验证前向是 bnb-4bit kernel 效率/带宽
> 瓶颈，不是调度瓶颈**，上文"13B 92% 是调度开销"的推断被推翻（阶段三
> "4bit≈bf16"正是 kernel 低效的表象）。13B 的正确药方是换 4bit kernel
> （AWQ/Marlin），见 verify_graph_fix.md 后续路线。
