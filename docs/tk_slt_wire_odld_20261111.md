### 终审之后追加的修复：跨设备随机流

Lead 在终审之后核对了当前版本的
[PyTorch multinomial 实现](https://raw.githubusercontent.com/pytorch/pytorch/v2.6.0/aten/src/ATen/native/Distributions.cpp)
及本机 CUDA 分布头文件。`torch.manual_seed` 会给各 GPU 同样的种子；
不同设备的默认 Philox 生成器若处于同一起点，草稿指数竞争与目标接受随机数
可重用第一个随机字。随机数之间不独立，不能只用“种子流有意变化”解释。

在源码对应的连续随机数模型中，`Q=[1/2,1/2]`、`P=[1/4,3/4]`、gamma=1：
提案 0 要求 `U0>U1`，接受 0 却使用同一个 `U0<1/2`，第一输出为 0 的概率
成为 `1/8` 而非 `1/4`。CPU 网格反例趋近该值；**这不是 GPU 实测结果**。
一项尝试用原生 CPU 生成器复刻相同消耗顺序的探针没有重现对齐，已保留负结果；
CPU/CUDA 的指数分布实现不同，不能混用其 RNG 消耗证据。

已作限定修复：一次 TK 解码拥有延迟初始化、按实际采样设备隔离的私有随机流，
覆盖提案、接受、standalone/fallback、残差和 bonus；同设备共用并持续推进生成器。
首次真实抽样从 CPU 默认 RNG 分配一次种子元数据，不是丢弃一个 token；模型前向
仍不抽样，构造/零预算/前置校验失败不取种子。不传送未计费的 P，不改共享概率数学。

公开解码入口还使用受控分类依赖模拟克隆默认角色随机带：旧路径输出 0 为 32/64，
私有流路径恢复 16/64（目标 1/4）；该替身采用逆 CDF，**不是 CUDA 指数竞争实测**。
这项反例与四项全路径生成器断言先红后绿，设备 key/推进/复现等结构测试 12 项通过。
Lead 审阅该后续改动并重跑了 v2 全量门禁；没有开启第二轮整批评审流水线。

实现子任务冻结后，Lead 补充了两个前置契约：载荷必须保持近似单位质量；
无效 prefix 范围和 top-K 类型必须在草稿前向前失败。两组均先红后绿。
整数/Decimal 的独立 oracle 不复用生产搜索，公共测试不依赖忽略目录或 mpmath。
